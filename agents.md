# Agent Instructions — Field Service Platform

These rules apply to any AI coding agent (Claude, Claude Code, or otherwise) working in this repository.

## Scope

- **Stay inside this repository.** Do not read, write, or reference files outside this project folder (no home directory dotfiles, no other repos, no system config).
- Do not access, print, log, or commit credentials, API keys, tokens, or `.env` files — this now includes `backend/.env` (DB password, JWT secret) as well as `employee_app/.env`. Both are git-ignored — never hard-code them in source.
- Do not run destructive git operations (force-push, history rewrite, branch deletion) without explicit confirmation from a human in the conversation.
- Do not modify already-applied migrations. This now applies to **`backend/src/main/resources/db/migration/`** (the live, current schema source of truth) — add a new Flyway version (`V2__...sql`, etc.) instead of editing `V1`. `supabase/migrations/` is historical only (see Project context) and shouldn't be edited either, for the same reason it never should have been.

## Project context

Field service operations platform for an owner managing remote, part-time, non-technical workers across multiple project sites.

- `employee_app/` — Flutter mobile app (Android + iOS) for workers: PIN login (no self-registration), clock in/out, availability, timesheet. A **thin UI client** — it holds no direct database or auth credentials at all, only a JWT for the backend below.
- `backend/` — **Java Spring Boot REST API. Owns all business logic, database access, authentication, and photo storage** for both `employee_app` (now) and `owner_dashboard` (later). Nothing talks to the database except this service.
- `owner_dashboard/` — React + Vite web dashboard for the owner (projects, sites, workers, assignments, per-worker availability/shifts). A **thin UI client** of `backend/`, same as `employee_app` — no database access, only a JWT.
- `supabase/` — **historical only.** The Postgres database is still physically hosted on Supabase (no local Postgres/Docker on this machine), but none of Supabase's client-facing features are used anymore — no Auth/GoTrue, no Storage, no PostgREST, no RLS. `supabase/migrations/` and `seed.sql` describe how the schema reached its pre-backend-migration state; `backend/src/main/resources/db/migration/` is the current source of truth going forward.

## Conventions

### Flutter/Dart
- Follow standard `flutter_lints` conventions. Keep screens in `lib/features/<feature>/`, shared data models in `lib/models/`, and all backend calls behind a `lib/services/` wrapper around the single `ApiClient` (`lib/core/api_client.dart`) — screens should never call `http`/`ApiClient` directly.
- **Naming**: `snake_case` for file names, `lowerCamelCase` for Dart variables/methods, `UpperCamelCase` for Dart classes.
- Keep the employee app screens simple and large-tap-target — the target users are non-technical and often on small phones in the field.
- **The Shift screen (`lib/features/clock/clock_screen.dart`, tab-labeled "Shift" — previously "Attendance", previously "Clock In/Out") is the reference pattern for low-literacy-friendly UI in this app**: each assignment (site + project pair) is its own large tappable card (`CircleAvatar` + location-pin icon in a color deterministically derived from the site id, so the same site is always the same color — there's no real per-site photo, and a random icon per site would imply a meaning that isn't there), not a text dropdown. **This redesign is deliberately scoped to this one screen only** — an earlier full-app graphical/localized redesign was built once this session and then explicitly reverted by the user; don't extend this pattern to Availability/Timesheet/Login unless specifically asked.
- **A worker can be assigned to more than one project, so Start/End Shift is an inline per-card toggle pill (`_buildToggleButton`), not one shared button below a picker.** Every assignment card shows its own green "🟢 Start" or red "🔴 End" pill; tapping Start clocks in immediately (no separate select-then-confirm step). Since the backend tracks an active shift by `siteId` only (not `projectId` — see `ShiftService.clockIn`), a card is "active" whenever `assignment.siteId == activeShift.siteId`; a worker with two assignments at the *same* site sees both cards go active together, since they genuinely share one underlying shift either card can end. Every other card is dimmed (`Opacity` wrapper) and its Start button disabled while any shift is active elsewhere, since only one shift can be open per worker at a time. Give the toggle pill a fixed `SizedBox` width (currently 92×44) rather than letting `ElevatedButton` size itself — leaving it unbounded inside the card's `Row` throws a `BoxConstraints forces an infinite width` layout exception at runtime (hit once during this build; `ElevatedButton`'s default unbounded `maximumSize` is the culprit once the surrounding widget isn't a plain `Material`/`InkWell` card anymore).
- **Ending a shift attaches 1-3 photos picked via `_showEndShiftSheet`'s bottom sheet, not a mandatory live camera capture.** Tapping an empty one of the 3 slots opens a small chooser (`_pickPhoto`: "Take photo" / "Choose from gallery" — both valid, since a worker documenting finished work doesn't need a fresh capture over an existing photo); a filled slot shows a thumbnail with a remove (×) button. Every photo is resized/recompressed *at selection time* via `ImagePicker`'s own `maxWidth`/`maxHeight` (1024) and `imageQuality` (60) — there is no separate server-side compression step, so if the compact-storage target ever needs to change, it changes here. "End Shift" stays disabled until at least one photo is attached; the sheet returns the picked `List<File>` to `_clockOut`, which posts them all under one `photos` multipart field name (see the Java section's `shift_photos` note).
- **Tab/title naming**: the bottom-nav tab and AppBar title for the clock-in/out screen are "Shift" (renamed from "Attendance", itself renamed from "Clock"/"Clock In/Out") — keep both in sync if either is touched again (`HomeShell._titles` and the `NavigationDestination` label in `lib/features/home/home_shell.dart`). No user-facing text should say "clock in"/"clock out" anywhere in the app — use "start shift"/"end shift" phrasing; internal identifiers that mirror the backend's JSON field names (`Shift.clockInAt`, `clockOutAt`, `ClockService`, `ClockScreen`) were deliberately left alone since renaming them has no user-visible benefit and would touch the API contract.
- **The Availability screen (`lib/features/availability/availability_screen.dart`) is a full-day toggle, not a time-range picker.** There is no time-of-day concept in the UI at all — tapping a calendar day immediately marks it available (green) or un-marks it, with no Save button and no separate confirmation step. Internally this is still represented as an `availability_slots` row spanning local midnight to the next local midnight (the schema still has a start/end timestamp range; the UI just never exposes it). A "Clear All" button (behind a confirmation dialog, since it's destructive) removes every marked day at once.
- **Toggle-style UI (Availability's day-marking, Shift's site select/deselect) must update optimistically and must never do a full-list refetch after a single-item mutation.** The Availability screen's first version called `fetchMySlots()` again after every add to pick up the server-assigned id, which (a) doubled the round-trip time per tap, and (b) could let one tap's late-arriving refetch wholesale-overwrite a *different*, more recently-tapped day's optimistic state — a real, user-visible flicker bug caught during testing. Fixed by having the add endpoint return the created row(s) directly (`AvailabilityService.addFullDayAvailability` returns `List<AvailabilitySlot>` instead of `void`) and merging just that response into local state. Any future single-item toggle UI should follow the same pattern: mutate local state immediately, use the mutating call's own response for anything you need back (an id, a computed field), and never re-fetch the whole collection just to learn what your own request already told you.
- **The Timesheet screen (`lib/features/timesheet/timesheet_screen.dart`) has Week and Month views (`SegmentedButton`), each with its own quick-jump picker** — tapping the period label ("Week of M/D" or "Month Year") opens a bottom sheet listing the last 12 weeks/months as tappable rows, rather than only stepping one at a time via the arrows. Both views call the same backend endpoint (`TimesheetService._fetchShifts`, hitting `/api/timesheet/week`) with a different-length date range — **do not add a separate `/api/timesheet/month` endpoint**, the existing one already takes an arbitrary `weekStart`/`weekEnd` range and doesn't care what you call it.
- **Timestamps**: always call `.toUtc()` on a `DateTime` before sending it to the backend, and always call `.toLocal()` before reading `.hour`/`.minute`/`.day` off a `DateTime` that came back from the API. The backend serializes everything as ISO-8601 UTC; Dart's `DateTime.parse()` does not auto-convert to local time. Skipping either step silently shifts times by the device's UTC offset — this exact bug hit clock-out, the clock-in display, and the timesheet query/display earlier, and hit the availability slot list *again* during the Supabase→backend migration (fixed, but a reminder that "already fixed once" doesn't mean "can't recur elsewhere").
- Any `Timer` (e.g. a periodic UI refresh) added to a `State` must be cancelled in `dispose()`.
- **Phone numbers are stored as a complete, standardized E.164 string** (`+<country dial code><national number>`, no spaces/dashes) — this replaced the earlier "stored exactly as typed" approach once the platform started deploying to multiple countries (US + India so far) and mixed formats (spaces, missing country codes, dashes) became a real source of confusion/duplicate-account risk. `service/PhoneNumberService.normalize(String)` is the single place every phone number passes through — on worker creation (`OwnerWorkerService`), login (`AuthService`), and the bootstrap owner (`BootstrapOwnerRunner`) — before it's ever stored or looked up. It strips incidental spaces/dashes/parens, requires a "+" country code, and validates the digit count against the configured country list (`config/PhoneProperties`, bound from `application.yml`'s `app.phone.countries` — the one place that lists supported countries; add a country there, no code change needed elsewhere). A login with a malformed/unsupported phone fails as a generic "Invalid phone number or PIN" (never leaks *why* it didn't parse, same as a wrong PIN) — see `AuthService.login`.
- **`GET /api/config`** (public, `permitAll`) is what both frontends fetch to render a country-code selector before a user has necessarily logged in — returns the same `PhoneProperties` list as `PhoneCountryResponse`s plus a `defaultCountry`. If a future setting needs the same "one backend-owned config, no admin UI" treatment, extend `AppConfigResponse` rather than adding a second config endpoint.
- **The Shift screen shows site name and project name, but not the worker's own name.** A worker-name greeting was tried and iterated on (small text → colorful gradient banner → plain text) and rejected at every stage via direct user feedback ("Deval seem very small", "Remove the Name banner looks not good", "Remove Hi Deval too") — a logged-in worker on their own phone doesn't need to be told their own name, and each attempt just added visual clutter above the actual task (tap a card). The screen now goes straight from the "Shift" title to the site-selection cards / active-shift card. `services/profile_service.dart` and `models/worker.dart` (the `GET /api/me` consumer) were deleted as dead code once the greeting was removed — the backend's `GET /api/me` endpoint itself is untouched, just unused by the mobile app now. Site/project info still comes from `ClockService.fetchMyAssignments()` (`GET /api/assignments`, replaced the old project-blind `/api/sites/assigned` now that a site can host more than one project) — the site-selection cards and active-shift card are driven by `Assignment` objects (`models/assignment.dart`, mirroring the backend's `AssignmentResponse`), not `Site` objects. A worker with two assignments at the same site (different projects) sees two cards, one per assignment, rather than a deduped single site card that would have to arbitrarily pick one project to display.
- **Never format a date as bare `month/day` numbers anywhere a worker sees it** (e.g. `'${d.month}/${d.day}'`) — flagged by an Indian user as unreadable, since `7/27` reads as day-first (27th of a nonexistent month 7... or the 7th of month 27) outside US convention. `timesheet_screen.dart`'s `_dateLabel(DateTime)` spells the month out (`'27 Jul'`) instead, and the week picker/header show a full range (`_weekRangeLabel`, `'27 Jul – 2 Aug'`) rather than just the start day. The existing `_monthYearLabel` ("July 2026") and `_timeLabel` (24-hour `18:36`) were already unambiguous and didn't need changing — only the two spots still doing raw numeric month/day did.
- **The login screen's country-code selector** (`features/auth/login_screen.dart`) fetches `GET /api/config` via `services/config_service.dart` (`lib/models/phone_country.dart` for the shape) and defaults to whatever `defaultCountry` the backend returns. The screen validates the entered digit count against the selected country's `nationalLength` client-side before ever calling the backend — a friendlier failure than waiting for the login attempt to bounce — but the backend's own `PhoneNumberService` is still the real enforcement point. There's no country selector anywhere else in this app since login is the only place a worker ever types a phone number (accounts are owner-provisioned — see below).
- **Worker accounts are owner-provisioned, not self-registered.** There is no in-app sign-up. An owner (authenticated with an OWNER-role JWT) calls `POST /api/owner/workers` `{fullName, phone, pin?}` to create one, and `POST /api/owner/workers/{id}/pin` `{pin?}` to reset a PIN later — `pin` is **optional in both**: if omitted/blank, the backend generates a random 6-digit PIN server-side (`OwnerWorkerService.generatePin()`, `SecureRandom`) and returns the *effective* pin (owner-supplied or generated) in the response exactly once (`CreateWorkerResponse`/`SetPinResponse`) — `ProfileResponse` never carries it. The backend hashes the PIN with `BCryptPasswordEncoder` and stores it in `profiles.pin_hash` — that hash **is** the actual credential now, checked directly by the backend's own login endpoint. There is no Supabase Admin API, no `auth.users`, no service_role key anywhere in this flow anymore.

### React (`owner_dashboard/`)
- **Plain JavaScript, no TypeScript, no UI framework, no state library** (no Redux/Zustand/React Query) — plain `useState`/`useEffect` per page and hand-written CSS (`src/index.css`). This matches the low-ceremony style of `employee_app`/`backend` elsewhere in this repo; don't introduce these unless the app's complexity genuinely outgrows the pattern.
- **Layout**: `src/api/client.js` (fetch wrapper — JWT attach, error normalization), `src/auth/` (`AuthContext`, `ProtectedRoute`), `src/layout/AppLayout.jsx` (fixed left sidebar — brand + nav + user/logout footer — with a single scrollable content column; no separate top bar), `src/components/` (small shared pieces like `PinRevealModal`), `src/pages/` (one file per route, page-local forms as unexported functions in the same file rather than a separate `components/` file per form).
- **Auth**: JWT + profile stored in `localStorage` (`token`, `profile` keys), rehydrated into `AuthContext` on load. `AuthContext.login()` explicitly rejects with a clear error if `profile.role !== 'OWNER'` — this dashboard must never let a WORKER-role login through, even though the backend's `/api/auth/login` endpoint itself doesn't distinguish dashboard vs. mobile callers.
- **Error handling**: `api/client.js`'s error handling must not assume every non-2xx response has a `body.error` string — see the `MethodArgumentNotValidException` handler note in the Java section below; fall back to a generic message if `error` is absent.
- **PIN display**: the create-worker and reset-PIN flows both funnel through the same `PinRevealModal` component — a PIN is shown out of a request's response exactly once and never re-fetched or persisted client-side beyond that modal's local state (there's no backend endpoint that could re-reveal it anyway, by design).
- **Each page's independent data fetches get their own `useEffect`**, not one combined effect — e.g. `WorkerDetailPage` fetches profile/assignments/availability/shifts separately, so one failing call doesn't block the others from rendering.
- **Phone number entry** (`components/PhoneInput.jsx`) is the one deliberate exception to "no shared component for a 2-page pattern" — `LoginPage` and `WorkersPage`'s create-worker form both need a country-code `<select>` + national-number `<input>` combined into an E.164 string via `buildE164()` right before submit, backed by `usePhoneCountries()` fetching `GET /api/config`. Duplicating this (not just a plain fetch, but fetch + two-piece state + concatenation logic) risked the two copies drifting apart, unlike the simpler single-endpoint-fetch duplication elsewhere in this app.
- **Charts are hand-rolled HTML/CSS (`components/BarChart.jsx`), not a charting library** — same "no new dependency" convention as the hand-rolled inline SVG icons. A horizontal bar list (label · track · direct-labeled value) covers every current need (magnitude by category); reach for something heavier only if a genuinely different chart form (time series, scatter) is needed. Colors reuse the app's own existing tokens (`--primary`/`--primary-dark` for the fill/hover, `--gray-soft` for the track) rather than introducing a parallel palette — every value is direct-labeled at the bar's end so the CSS-only hover highlight is a nice-to-have, never the only way to read a number. Caps at 8 rows, folding the rest into a single "Other (`n`)" bar, so a long tail of categories doesn't make the list unreadable.
- **A shift only carries a `siteId`, never a `projectId` (see the Java section's Site/Project invariant), so attributing a shift's hours to a project is a best-effort join through assignments, not a stored fact.** `ReportsPage` resolves each shift's project by looking up `(workerId, siteId)` against every assignment (`GET /api/owner/assignments`, all workers): exactly one match → that project; zero matches → "Unassigned"; two or more (a worker assigned to multiple projects at the same site) → bucketed as `"<site name> (multiple projects)"` rather than guessing which one. Don't try to "fix" the ambiguous case by splitting hours evenly across the tied projects — that fabricates precision the data model doesn't have; the honest answer is a clearly-labeled bucket.
- **Visual identity is "Blueprint"** — a deep-cobalt accent (`--primary: #1d4e89`), sharp-ish corners (`--radius-sm: 6px` / `--radius-md: 8px` / `--radius-lg: 10px`, never the old 14–16px), a dark-navy fixed sidebar (`--sidebar-bg: #0e1c33`), and the `Segoe UI` system-font stack — chosen (from three pitched directions) to read as dense/technical/Dynamics-adjacent rather than a consumer app, since the owner is evaluating this against Zoho/Dynamics. **Every color is a token in `:root`** (`--primary`, `--good`/`--warn` for status, `--sidebar-*` for the nav rail) — a page or component should reference the token, never hardcode a hex, so a future re-theme is a one-file edit. The old multi-hue tile system (`--blue`/`--purple`/`--orange`/`--teal` gradients on the Home tiles) was deliberately removed in favor of one consistent accent — a dense enterprise dashboard reads as more credible with restrained, controlled color than a rainbow of gradient tiles.
- **`HomePage` is a real dashboard, not a nav-shortcut grid — every number on it is a live query, never fabricated.** Four clickable stat tiles (Sites/Active Projects/Workers/Hours-this-month, `.stat-tile-link`, each navigates to its section), a "Recent activity" panel derived from `GET /api/owner/shifts` for the current month (one row per shift — an still-open shift renders as "clocked in" with a pulsing `.dot-live`; a finished one renders as "completed a shift — N hrs"; sorted by whichever timestamp is most recent), a "Hours by site" `BarChart` (same component `ReportsPage` uses), and a "Sites" panel (name/company/active-project-count, derived by counting `projects` per `siteId`). There's no generic activity-log endpoint on the backend — the feed is inferred client-side from shift rows the owner already has access to, not a new audit-trail feature; don't add a `confirmed` row alongside a shift's own completed/clocked-in row, since that would show the same shift twice with no second real timestamp to justify it. `src/lib/hours.js` now holds `formatHours`/`hoursOf`/`aggregateHours` (previously duplicated only in `ReportsPage`) so `HomePage` and `ReportsPage` can't drift on the hours math — extend that file, don't re-derive the formula a third time. The "+ New worker" button in the page header navigates to `/workers` with router state (`{ openForm: true }`) rather than duplicating `WorkersPage`'s create form; `WorkersPage` reads `useLocation().state?.openForm` once on mount to decide the form's initial `showForm` value.

### Java / Spring Boot (`backend/`)
- **Package layout**: `config/`, `security/` (JWT), `controller/`, `service/`, `repository/`, `entity/`, `dto/`, `exception/`. Controllers return DTOs, **never entities directly** — avoids accidentally leaking `pin_hash`.
- **No ORM. `entity/` holds plain POJOs, not JPA `@Entity` classes; `repository/` classes are hand-written `@Repository`-annotated wrappers around Spring's `NamedParameterJdbcTemplate`, not Spring Data JPA interfaces.** This was a deliberate mid-project replacement of Hibernate (see Status below for why) — do not reintroduce `spring-boot-starter-data-jpa`, `@Entity`/`@ManyToOne`/`@Enumerated`, or a `JpaRepository`/`Specification` anywhere.
- **Entities hold foreign keys as raw `UUID` fields** (e.g. `Shift.workerId`, `Shift.siteId`), never nested object references (no `Shift.getWorker()`). This structurally rules out the entire lazy-loading bug class — there is nothing to lazily fetch, so there's no `LazyInitializationException` to guard against and no need for `@Transactional(readOnly = true)` purely for that reason. `@Transactional` is still used, but only for genuine multi-statement atomicity (e.g. `ShiftService.clockOut()`'s upload-then-update).
- **Repository conventions**: single-row CRUD (`insert(entity)`, `findById(id)`) returns the plain entity; `insert()` generates the `UUID` itself (`if (id == null) id = UUID.randomUUID()`) right before the `INSERT`, then re-reads the row — there's no shared base class or `@PrePersist` doing this centrally, every repository does it inline. Multi-row reads that need denormalized fields (a site's project name, a shift's worker/site names) get their own distinctly-named method (e.g. `findResponsesByWorkerId`) whose `RowMapper` builds the **response DTO directly** via a SQL `JOIN` — bypassing the plain entity for that read entirely. Don't add a redundant read on a write path that already has the parent object in scope (e.g. `ShiftService.clockIn` already holds `Profile worker` + `Site site` and builds the `ShiftResponse` manually).
- **`profiles.role` and `shifts.status` are plain `varchar` + `check` constraint columns, not Postgres enum types** — `Role`/`ShiftStatus` are plain enums with `toDbValue()`/`fromDbValue()` static helpers for the lowercase-DB ↔ uppercase-Java mapping. Use them for **every** read, write, and filter parameter that touches one of these columns (`OwnerWorkerService`, `BootstrapOwnerRunner`, `ShiftService`, any status filter in a search/timesheet query) — there's no `@Enumerated`/`AttributeConverter` doing this automatically anymore, so a spot that binds the enum's raw `.name()` instead of `.toDbValue()` will violate the DB check constraint.
- **Dynamic SQL with optional filters** (e.g. `ShiftRepository.searchForOwner`'s owner shift search): build the `WHERE` clause with a `StringBuilder`, and append a fragment *and its parameter together, as one atomic step*, only when that filter is actually non-null. Never add a parameter to the param map without also adding its clause — an unbound/mismatched parameter is exactly what caused the original Hibernate-era `could not determine data type of parameter` failure (from a JPQL `"(:x is null or ...)"` pattern), and hand-written SQL can reintroduce the same failure mode just as easily if a clause and its parameter ever get out of sync.
- **Dedup in SQL, never in Java, for list reads built from a `RowMapper`.** A plain POJO has no `equals()`/`hashCode()` override, so `.stream().distinct()` on freshly-built rows silently falls back to reference equality and stops deduping. `AssignmentRepository.findDistinctSitesForWorker` — a worker assigned to the same site via two assignment rows must still only appear once — uses SQL `GROUP BY` on the site's own columns instead. Any future list-with-dedup requirement needs the same treatment.
- **Authorization lives entirely in the service layer — there is no Postgres RLS.** Every worker-facing service method must scope its query by the authenticated principal's id (never a client-supplied id), and every mutation must verify record ownership before acting using flat `UUID` equality (e.g. `shift.getWorkerId().equals(worker.getId())` — see `ShiftService.clockOut()`'s `AccessDeniedAppException` check as the pattern to copy). Every owner-only endpoint needs `@PreAuthorize("hasRole('OWNER')")`. Convention: a "worker A cannot touch worker B's data" check for every new mutating endpoint — this exact bug class (IDOR) is what RLS used to prevent for free.
- **`SecurityConfig`'s permit-all list must include `/error`.** Without it, any unhandled exception that resolves via `HttpServletResponse.sendError(...)` (which is how Spring MVC's default/`DefaultHandlerExceptionResolver` handling works, e.g. for `MethodArgumentNotValidException` when no `@ExceptionHandler` matches) triggers a servlet container ERROR dispatch to `/error` — and since that's a fresh dispatch, `JwtAuthenticationFilter` doesn't re-authenticate it, so Spring Security's `anyRequest().authenticated()` rule rejects it and the client sees a **misleading 401 "Unauthorized" instead of the actual error status** (400, 500, whatever it should have been). Found and fixed while building `owner_dashboard`: a validation failure on `POST /api/owner/workers` (missing `fullName`) was returning 401, not 400. `GlobalExceptionHandler` now also has an explicit `MethodArgumentNotValidException` handler returning `{"error": "<field> <message>"}` in the same shape as every other error, instead of leaving `@Valid` failures to Spring Boot's differently-shaped default body.
- **CORS**: `config/CorsConfig.java` defines a `CorsConfigurationSource` bean (allowed origins from `app.cors.allowed-origins`, env-driven, defaulting to Vite's dev/preview ports), wired into `SecurityConfig` via `.cors(Customizer.withDefaults())`. Needed because `owner_dashboard` runs on a different origin/port than the backend (the mobile app isn't subject to browser CORS at all, which is why this was never needed before). If you add a new frontend origin (a deployed dashboard URL, a different dev port), extend `CORS_ALLOWED_ORIGINS` rather than hardcoding a new origin in Java. **`config.setAllowedMethods(...)` must list every HTTP method any frontend actually calls** — `PATCH` was missing (only `GET/POST/PUT/DELETE/OPTIONS` were listed) and the dashboard's project-status toggle silently failed as an unlabeled browser-level CORS preflight rejection (`Failed to fetch`, no server-side error at all) until this was caught during Site/Project inversion testing. If a new frontend mutation uses a method not already in this list, add it here first.
- **Audit-style "who/when" columns are stored but not always returned.** `shifts.confirmed_by` (who confirmed a completed shift) follows the same pattern as `assignments.assigned_by`: stored in the DB for accountability, but deliberately left out of the response DTO (`ShiftResponse` only exposes `confirmedAt`, not a confirmer name/id) since nothing has asked to display "who." If a future feature needs to show who confirmed/assigned something, add the field then rather than pre-emptively — don't infer a need for it from the column's mere existence.
- **Site/Project inversion invariant**: a `Project` belongs to exactly one `Site` (`projects.site_id`, set once at creation via the `POST /api/owner/sites/{siteId}/projects` path variable) — **never add an endpoint that lets a project's `site_id` change after creation.** `AssignmentService.createAssignment` relies on this: it derives `assignments.site_id` from the loaded `Project.getSiteId()` itself rather than accepting `siteId` from the caller (`CreateAssignmentRequest` only has `projectId`/`workerId`), which is what makes an assignment's (project, site) pair impossible to get out of sync — there's no cross-check needed because there's only one writer and no mutator. If a "move project to a different site" feature is ever requested, treat it as a deliberate exception to this invariant, not a quick field update — it invalidates every existing assignment's site derivation for that project's workers.
- **A shift can have up to 3 clock-out photos, stored in a separate `shift_photos` table (`shift_id`, `position` 0-2, `unique(shift_id, position)`), not a single `shifts.clock_out_photo_url` column** (`V4__add_shift_photos.sql`). `ShiftRepository`'s single-row `RowMapper` can't express a one-to-many join, so `RESPONSE_ROW_MAPPER` always leaves `clockOutPhotoUrls` empty and every method that returns a `ShiftResponse` (or list of them) must pipe its result through `attachPhotos()` before returning — a second query batched by shift id, not N+1 per shift, that also builds each URL as `'/photos/' || id::text` on the fly (see the DB-backed-photo-storage bullet below — there's no stored `photo_url` column anymore). `WorkerShiftController.clockOut` takes `@RequestParam("photos") List<MultipartFile>` (repeated parts under the same field name, not an array-style name); `ShiftService.clockOut` throws `IllegalArgumentException`/400 if the count isn't 1-3 before touching the shift or storage at all, then loops calling `photoStorageService.store(shiftId, position, file)` once per photo, in list order, so `position` reflects upload order.
- **Clock-out photos live in the database, not on disk** (`V5__store_photos_in_database.sql`: `shift_photos` gained `data bytea` + `content_type`, `photo_url` was dropped). `DatabasePhotoStorageService` (the only `PhotoStorageService` implementation now — `LocalFilesystemPhotoStorageService` and its `WebConfig` static-resource mapping were deleted, not kept as a dead alternative) inserts the row directly and returns `/photos/<id>`; a new public `PhotoController.getPhoto()` reads `content_type`/`data` back out by id and serves them — same `permitAll` `/photos/**` pattern as before, so neither frontend needed a code change (they were already treating the field as an opaque URL string). This was a deliberate choice over S3 for where the app is right now: one durable store that rides along with the existing Postgres backups, no separate file storage to provision, and `ShiftService.clockOut`'s multi-photo insert-then-complete sequence is now genuinely all-or-nothing in one SQL transaction (the old filesystem write couldn't roll back with the DB update if something failed partway). Revisit only if photo volume genuinely outgrows keeping them in Postgres — the interface is still the seam to swap through.
- **`PhotoRetentionService`** is a daily `@Scheduled` job (`0 0 3 * * *`, needs `@EnableScheduling` on `BackendApplication`) that deletes `shift_photos` rows once their shift's `clock_out_at` is older than `app.photo-retention.days` (env `PHOTO_RETENTION_DAYS`, default 30) — one flat rule, deliberately no separate branch for confirmed-vs-unconfirmed shifts (that was considered and dropped for being unnecessary complexity). Change the retention window via config, not code. `ShiftRepository.deletePhotosForShiftsClockedOutBefore(cutoff)` is the query it calls, single-purpose and reusable if a manual/on-demand purge is ever needed.

## Environment notes

### Backend (Java)
- Needs Java 21 + Maven (confirmed installed via Homebrew as `openjdk@21` / `mvn`). No local Postgres or Docker is installed on this machine — the backend connects directly to the same Supabase-hosted Postgres via JDBC, not a local database.
- Config lives in `backend/.env` (git-ignored) — copy `backend/.env.example` and fill in `DB_URL`/`DB_USERNAME`/`DB_PASSWORD` (the **database password** from Project Settings → Database, not the anon/publishable API key — different credential, different protocol) plus `JWT_SECRET`/`BOOTSTRAP_OWNER_*`/`PHOTO_RETENTION_DAYS`. Spring Boot doesn't load `.env` files natively — run with: `set -a && source backend/.env && set +a && mvn -f backend spring-boot:run`.
- **Supabase's direct-connection hostname (`db.<ref>.supabase.co:5432`) is IPv6-only.** If the network has no IPv6 route (common), JDBC fails with `NoRouteToHostException`. Use the connection **pooler** instead (Project Settings → Database → Connection Pooling): host `aws-<N>-<region>.pooler.supabase.com`, username becomes `postgres.<project-ref>` (not plain `postgres`). The numeric prefix (`aws-0-`, `aws-1-`, ...) is specific to which pooler node your project's tenant is actually registered on — the wrong number gives `FATAL: (ENOTFOUND) tenant/user ... not found`, which reads like a routing problem but isn't one.
- **The pooler caps total concurrent session-mode clients project-wide** (`pool_size: 10` observed in practice). HikariCP's default max pool size (10) can exhaust this alone, leaving no room for a concurrent `psql`/`pg_dump` check. `application.yml` pins `hikari.maximum-pool-size: 3` for this reason — reconsider before any multi-instance deployment.
- **The Supabase pooler is in a different AWS region than wherever this backend actually runs, and that costs a real, measured ~300-600ms round trip per new physical connection** (confirmed via a raw TCP-connect timing test to the pooler host, not guessed) — on top of that, every query on an already-established connection still pays a real network-latency tax per round trip, confirmed by comparing `/api/ping` (no DB, ~1.5ms) against any DB-touching endpoint (0.8-2.3s even on repeated/warm-connection calls). This is a geography fact, not a query-performance problem — don't go looking for a missing index or an N+1 query first if something feels slow; time `/api/ping` vs. a DB endpoint to confirm it's the same network-distance tax before assuming otherwise. `hikari.maximum-pool-size`/`minimum-idle` are both set to 5 (not the original 3/1) specifically so `minimum-idle == maximum-pool-size` keeps every connection warm, and so a page firing several concurrent requests (Worker Detail fires 5) doesn't have some of them queue for a connection *in addition to* the unavoidable per-request network latency — confirmed via a 5-way concurrent `curl` burst dropping from queued/serial to ~1.1s total once the pool had enough warm connections to serve all 5 at once. Revisit the pool size again if a page ever needs more than 5 concurrent DB-touching requests, and reconsider whether every page-load genuinely needs that many round trips in the first place before just bumping the number further.
- Flyway is **baselined** (`baseline-on-migrate: true`, `baseline-version: "0"`) because it runs against the already-populated Supabase database, not a fresh one. `V1__migrate_from_supabase.sql` **alters** the existing schema in place (drops the `auth.users` FK, all RLS policies, GRANTs, `is_owner()`/`set_employee_pin()`; adds the `profiles.phone` unique constraint; converts `profiles.role` from enum to varchar) rather than issuing fresh `CREATE TABLE`s. It deliberately leaves Supabase's own `auth.*`/`storage.*` schemas and platform event triggers (`ensure_rls`, `pgrst_ddl_watch`, etc.) untouched — not ours to touch, and harmless now that nothing depends on them.
- Flyway owns the schema outright — there's no Hibernate `ddl-auto=validate` startup check anymore (removed along with JPA). A repository/entity that drifts from the actual schema only surfaces as a runtime SQL error from that specific query, not a startup-time failure. Add a new Flyway version (`V2__...sql`, etc.) for any schema change; never edit `V1` after it's been applied.
- A ready-made Postman collection lives at `backend/postman/field-service-platform.postman_collection.json` — covers every endpoint (auth, owner CRUD, worker-facing clock-in/out/availability/timesheet), with test scripts that auto-chain tokens/ids into collection variables. Use it for manual data-seeding/testing instead of hand-writing curl each time.

**The backend was then further migrated off Spring Data JPA/Hibernate onto plain Spring `NamedParameterJdbcTemplate`** (see the Java/Spring Boot conventions above for the resulting rules). ## Known gaps / next up

- No automated tests exist for the backend or `owner_dashboard` yet. The "worker A cannot touch worker B's data" property was verified manually via curl during the JDBC migration but isn't regression-tested.
- `owner_dashboard` has no notification wiring (push/email/SMS on new assignment) — the dashboard can create the assignment row, but the worker isn't proactively told about it yet.
- `owner_dashboard` has no project/site edit or delete UI — only create + list, matching what was explicitly asked for. Add `PUT`/`DELETE` endpoints + forms if that becomes a real need.
- Photo retention (`PhotoRetentionService`) has no admin UI or manual-trigger endpoint — the only way to change the window is the `PHOTO_RETENTION_DAYS` env var, and the only way to run a purge outside the daily 3am schedule is to call `ShiftRepository.deletePhotosForShiftsClockedOutBefore` directly. Add an owner-facing "purge now" action or a settings field if that becomes a real need.
- JWTs are long-lived (30 days) with no refresh/revocation mechanism — a deliberate simplicity tradeoff for a small trusted user base, not an oversight. Revisit only if forced logout/invalidation is ever actually needed (e.g. via a `token_version` column).
- No CI yet. A free-tier deploy path exists (`backend/Dockerfile`, `render.yaml`, `owner_dashboard/vercel.json`) for demo/trial use — see `DEPLOYMENT.md` — but it's a manual click-through-the-dashboards process, not automated, and the Render free plan's cold-start-after-idle tradeoff makes it unsuitable as-is for real production traffic.
